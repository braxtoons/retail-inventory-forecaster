## ADDED Requirements

### Requirement: Rolling-origin cross-validation with production future frames
The system SHALL evaluate a product with a rolling-origin loop whose cutoffs are generated by `prophet.diagnostics.generate_cutoffs` with configurable `initial` (default 365 days), `horizon` (default and maximum 90 days) and `period` (default 60 days). Each fold SHALL fit a model from the same `build_model(config)` factory used in production, and predict on a future frame built by the same function production uses, as of the fold's cutoff.

#### Scenario: Same configuration as production
- **WHEN** cross-validation runs for a configuration
- **THEN** each fold's model is built by `build_model` with that configuration and its future frame by the production future-frame builder

#### Scenario: No future leakage
- **WHEN** a fold with cutoff C is fitted
- **THEN** the model sees no `y` or regressor value dated after C except calendar holidays and planned promotions

### Requirement: Selection and test folds
The system SHALL designate the last 3 cutoffs as test folds. It SHALL designate as selection folds the earlier cutoffs whose forecast window ends on or before the first test cutoff, and SHALL drop folds that overlap the test period.

#### Scenario: Headline from test folds
- **WHEN** an evaluation completes
- **THEN** headline metrics, skill and verdicts are computed from test folds only, and ablation scores are labelled as selection-fold results

#### Scenario: Insufficient history
- **WHEN** a product's history in the training window cannot yield 3 test folds and 3 selection folds
- **THEN** the evaluation job skips the product, reports the minimum history required, and does not fall back to a single split

### Requirement: Baseline comparison
The system SHALL evaluate naive (last observed value) and seasonal-naive (value 7 days earlier, repeating the last observed week) baselines on the same folds and horizons as Prophet. Where a required lag is a missing date, the most recent prior observation is used.

#### Scenario: Model vs baseline
- **WHEN** an evaluation completes
- **THEN** the result contains metrics for Prophet, naive and seasonal-naive per horizon bucket, plus Prophet's skill `1 − WAPE_prophet / WAPE_seasonal_naive`

### Requirement: Accuracy metrics by horizon bucket
The system SHALL report MAE, RMSE, WAPE, zero-safe MAPE (with the count of excluded zero-actual rows) and 95% prediction-interval coverage, per fold and aggregated, for horizon buckets 1–7, 8–30, 31–90 days and overall.

#### Scenario: Zero-sales days
- **WHEN** actual values contain zeros
- **THEN** MAPE excludes those rows and reports how many were excluded, and WAPE is computed over all rows

#### Scenario: Hand-computed example
- **WHEN** metrics are computed for a small known set of actuals and forecasts
- **THEN** each metric equals the hand-computed value

### Requirement: Regressor ablation
The system SHALL score the arms none, holidays, holidays+promo, holidays+oil and holidays+promo+oil on selection folds. It SHALL select a configuration greedily starting from holidays-only, accepting a change only if it lowers overall selection WAPE by at least a configurable relative margin (default 2%) and wins in at least a configurable share of selection folds (default 2/3). The full ablation table SHALL be stored and returned.

#### Scenario: Regressor does not help
- **WHEN** adding oil price does not meet both the margin and the fold-win share
- **THEN** the selected configuration excludes oil price and the ablation table shows its score

#### Scenario: Synthetic ground truth
- **WHEN** evaluation runs on the synthetic dataset
- **THEN** the selected configuration includes promotions and excludes oil price

### Requirement: Verdict vs seasonal-naive
The system SHALL assign each product and horizon bucket one verdict:
- `beats` when skill ≥ +5% and Prophet wins in at least 2/3 of test folds;
- `worse` when skill ≤ −5% and Prophet loses in at least 2/3 of test folds;
- `comparable` otherwise.

Both thresholds are configurable.

#### Scenario: Small difference
- **WHEN** Prophet's skill in a bucket is +2%
- **THEN** the verdict is `comparable`

### Requirement: Service-level calibration
The system SHALL record, for each test fold, whether actual demand over the default lead time was at or below the forecast reorder point at the default service level. It SHALL report the achieved cycle service level per product and pooled across products.

#### Scenario: Calibration reported
- **WHEN** an evaluation completes
- **THEN** the stored results include the achieved service level alongside the target

### Requirement: Offline evaluation job
The system SHALL run evaluation through a command-line job (`python -m evaluate --all | --product <id>`) using process-level parallelism, and SHALL NOT expose an API endpoint that triggers evaluation.

#### Scenario: Not yet evaluated
- **WHEN** a client requests accuracy for a product with no evaluation run
- **THEN** the system returns 404 with a message naming the evaluation command
